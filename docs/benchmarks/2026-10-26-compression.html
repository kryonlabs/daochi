The fastest practical HTTP candidate is reusable Go Zstandard in its fastest mode, with literal entropy compression explicitly enabled. Pre-encryption record packing delivers the larger bandwidth gain. These are local synthetic measurements; production rollout remains a separate gate.

What changes the decision

  • Default Go Zstandard can store large encrypted/base64 pages nearly uncompressed. The explicit WithAllLitEntropyCompression(true) option is required for this workload.
  • Brotli 11 offers a small extra saving on encrypted pages at a large CPU cost. LZ4 is fast but saves little on those pages and is not a standard browser HTTP content coding.
  • The current Go gzip encoder is much faster than zlib gzip at level 1. Algorithm names alone are insufficient; implementation and reuse matter.
  • Retain at most four idle encoder contexts initially. Four Zstandard fastest writers retain about 11.3 MiB of Go heap here, versus 4.6 MiB for gzip and 46.2 MiB for Brotli 4.

Method, versions and limitations

15 deterministic synthetic corpora, 228 bytes–4,058,818 bytes. Records use generated UTF-8 structured JSON, and simulated ciphertext uses uniform pseudorandom bytes. Real encrypted content is not inspected. The record packing pair starts from identical generated plaintext records; encryption is modeled by equal-length random bytes, so crypto CPU and nested-envelope overhead are excluded. Do not interpret the packing percentage as a forecast of user data.

A 16 KiB dictionary was trained on separate synthetic records with distinct IDs and a different seed; dictionary training and download cost are excluded from codec timing. Dictionary wins need amortization and a new negotiated record format.

Go Zstandard modes are library presets, approximately corresponding to native levels 1/3/7/11; levels are not directly comparable across libraries. Native bindings include allocation/copy overhead. Go reuse measurements keep output buffers warm; streaming HTTP and retained-memory measurements are separate. Empirical p95 with small sample counts is coarse, especially high-effort codecs. No phone energy, packet loss, target server, TLS or production tail latency has been measured. The benchmark run itself did not change or deploy production code; see the compression guide for current behavior.
